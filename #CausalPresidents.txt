Nigeria Presidential Performance Dashboard — Final README
Version: 1.0
Scope: Free-tier-only build. No paid service required at any layer.
Audience: Build agent. This document is the complete specification. Where decisions are marked [LOCKED], do not change them. Where marked [OPEN], confirm with the user before proceeding.

1. Purpose and Intent
Build a live, monthly-refreshed dashboard comparing national-level outcomes across Nigerian presidential administrations (1999–present) on health, education, security, and economic metrics. Overlaid indexed trend lines, colored by party or president, with portraits anchored under each tenure. A confounding-adjustment layer so that party and tenure effects can be argued rather than asserted. A natural-language Q&A layer grounded in the dashboard's own data and methodology.

The dashboard is not a causal-claim engine. It is a transparent, reproducible, regularly updated platform for forming and defending estimates. Every visual and methodological choice serves this intent.

Central tension, stated openly: presidential influence on Nigerian outcomes is heavily mediated by state governments, oil price cycles, donor funding, and inherited conditions. The dashboard shows these confounders rather than hiding them.

2. Non-Goals (v1)
No state-level or LGA-level breakdowns

No cross-country comparison

No causal claims — adjusted associations only, with confidence intervals

No sub-monthly refresh; monthly batch is the target

No user accounts, comments, or social features

No mobile-optimized layout

3. Language Split [LOCKED]
Layer	Language	Rationale
Ingestion (API calls, Prefect flows)	Python	Prefect is Python-native; API clients are Python-first
Transformation (dbt models)	SQL	dbt is SQL-first regardless of language choice
Dashboard (Streamlit + Plotly)	Python	One deployment surface, one runtime
Portrait processing	Python	Trivial batch job at ingest
Econometric adjustment (VECM, ARDL, DiD, SCM)	R	Reference implementations; better-documented than Python equivalents
NLP Q&A orchestration	Python	Integrates directly with Streamlit
R–Python boundary: R runs as a batch job in the monthly pipeline. It reads from a Postgres staging table and writes adjusted estimates back to an analytics table. Python never calls R at request time. The dashboard reads only pre-computed values. This keeps end-user latency at zero and keeps econometrics reproducible as standalone scripts.

9. Confounding Adjustment Framework [LOCKED — Tier 1 default]
Five tiers. Default view is Tier 1. Each tier adds rigor at cost of transparency.

Tier 1 — Raw indexed comparison
Baseline. No adjustment. Matches the user's example (Yar'Adua rise, then fall after party transition).

Tier 2 — Inherited-conditions flag
First 8–12 quarters of each administration flagged. Rationale: outcomes in the first two years are shaped by inherited policy and conditions. Toggle to include or exclude from scoring.

Tier 3 — Oil-price and fiscal-space adjustment (VECM / ARDL)
The core adjustment for Nigerian confounding. Include:

Brent crude (logged)

FAAC allocation to states

NGN/USD exchange rate

Lagged outcome variables (up to 4 lags)

Party dummy

Linear and quadratic time trend

Specification: Error-correction model. Test for cointegration first (Johansen). Fall back to ARDL bounds testing if series are not integrated of the same order.

Output: Long-run multiplier for party effect, with confidence intervals.

Interaction requirement: Interact oil price with administration dummies so the model estimates whether presidents responded differently to the same shock. Do not partial out oil as a nuisance — it is the dominant exogenous feature of Nigerian political economy.

Tier 4 — Difference-in-Differences with state alignment
Deferred to v2. User has stated national-level only.

Tier 5 — Synthetic control for tenure effects
Deferred to v2. Five administrations gives too small a donor pool. Cross-country comparison introduces incompatible institutional contexts.

Party vs. tenure interaction [LOCKED]
Present party effects stratified by tenure (PDP first term, PDP second term, APC first term, APC second term) rather than aggregating. Literature suggests first- and second-term effects differ systematically.

Sample-size constraint [LOCKED — acknowledge openly]
Five administrations, ~26 annual observations. VECM with oil price, FAAC, FX, and party dummies consumes degrees of freedom quickly. Expect wide confidence intervals. Never present a point estimate without its interval.

11. NLP Q&A Component [LOCKED — RAG approach]
Purpose: Natural-language question answering grounded strictly in the dashboard's data and methodology.

Architecture:

User question (Streamlit chat input)

Embed question locally (sentence-transformers, all-MiniLM-L6-v2)

Retrieve top-5 chunks from pgvector on Neon

Build prompt: system instruction + retrieved chunks + question

Call Groq (Llama 3.3 70B) or Gemini fallback

Parse response, extract citations, display with source links

Latency budget: embedding (~50 ms local) + vector query (~10 ms) + LLM (~500 ms on Groq) = under one second.

Corpus to index:

Metric catalog — one chunk per metric (label, unit, direction, source, frequency)

Methodology page — one chunk per adjustment tier

Data dictionary — column definitions, imputation methods, vintage notes

Shock annotations — one chunk per shock

Administration table — one chunk per president

Limitations section — chunked so the LLM can retrieve and cite caveats

Critical constraint [LOCKED]: The LLM must be instructed to say "I don't have data on that" when retrieval returns nothing relevant. A RAG system that hallucinates is worse than no RAG system.

Evaluation: RAGAS in CI on a small test set of question-answer pairs. Measures faithfulness, answer relevance, context precision, context recall.

UI additions:

Sidebar tab "Ask the data"

Chat input and message history

Source citations as expandable blocks

Starter question buttons: "What was under-5 mortality under Yar'Adua?", "Which president had the highest inflation?", "How did the 2016 recession affect security metrics?", "Compare PDP and APC on immunisation."

End-to-end ownership — API ingestion → orchestration → warehouse → dbt → econometric adjustment → RAG → dashboard → monitoring

Methodological rigor — cointegration tests, CIs, RAGAS evaluation, explicit limitations

Engineering discipline — Prefect orchestration, dbt tests, CI/CD, vintage tracking, monitoring
